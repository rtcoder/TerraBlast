## Zgodność i zakres

Zostaje JSON/ENet version2. Legacy hello bez role/extensions oznacza player. Nowe pola są opcjonalnymi rozszerzeniami; lobby roster graczy i MatchState.players pozostają bez zmian. Nowy server przyjmuje starych klientów. Nowy spectator wymaga potwierdzonego role=spectator i nie ufa staremu serverowi, który ignorując hello przydzieliłby player: po takim snapshot klient rozłącza się z błędem unsupported_spectator_server. Nie obiecujemy obsługi obserwacji przez dawny server. Bez promocji/demotowania uczestników w aktywnym połączeniu, prywatnych wiadomości, Nakama chat i zdalnego admin API.

## API i wire

* MatchClient `connect_to_server(host:String="127.0.0.1",port:int=19170,role:String="player")->Error`; dotychczasowe wywołania działają. `requested_role`, potwierdzone `role`, `spectator_id`; player_id=="" dla widza. `retry_connection()` zachowuje rolę, role/endpoint change czyści token. `leave()` wysyła reliable leave+flush, close() zachowuje token. `status_snapshot` dodaje role/requested_role/spectator_id. Gameplay send functions mają jawny guard role==player.
* Hello `{type:"hello",resume_token,role?,extensions?:["spectators_v1","chat_v1"]}`. Lista max8 krótkich stringów; nieznane extension ignorowane, nieznana rola odrzucona. Resume token nadal hex64. Capabilities per peer tylko w bounded autoryzowanej tabeli, nie są dowodem uprawnień.
* Opcje: `spectator_capacity:int=0` zakres0..6, `chat_enabled:bool=false`. Options.apply rozszerzyć o ścisłe typy tych pól bez osłabienia istniejących liczb. Server start signature zostaje. ENet max32: max16autoryzowanych tożsamości (10player+6spectator) i bounded pending, hello timeout nadal obowiązuje. Slot reservation liczy się do limitu swojej roli.
* Server osobne `spectators[peer_id]={id,name}`, `spectator_reservations[token]={id,name,peer,expires}`; slots/reservations graczy zachowują obecne znaczenie. Centralny helper listy odbiorców autoryzowanych zastępuje `for id in slots` wyłącznie w broadcast/snapshot/reset/shutdown. Quorum i _phase zawsze slots. Reconnect token nigdy nie przekracza roli.
* Snapshot nowych uczestników dodaje `role`, `spectator_id`; dla widza player_id="". Legacy snapshot player nadal poprawny bez role. Protocol.valid_snapshot_metadata ma rozłączne gałęzie i nie akceptuje pustego id dla zwykłego player. Snapshot_end player membership obowiązkowe tylko w roli player. Rola nie jest mutowana przez state/result/lobby.
* Lobby optional `{spectator_capacity:int,spectators:[{id,name,connected}]}`; max6, unikalne id, nazwa przez istniejący valid_display_name. Rezerwowany widz ma connected=false. Player roster ma dokładnie capacity rekordów jak dotychczas.
* Widz ma tylko ping/snapshot/display_name/chat/leave. Centralna server zapora odrzuca command/move/surrender/restart/ready/rematch przed jakimkolwiek slots[sender]. Cleanup widza nie czyści player votes ani motion. Frozen snapshots i catchup pozostają jedną wspólną ścieżką; overflow supersedes snapshot także widzowi; round robin współdzielony.
* `LobbyChat` nowy RefCounted: `valid_text(value)->bool`, `append(author:Dictionary,text:String,nonce:String,generation:int,now_ms:int)->Dictionary`, `history()->Dictionary`, `reset(generation:int)`, `forget_identity(id:String)`. Model bez transportu, zegar wstrzykiwany. Max256znaków/1024bajtów wiadomości, bez znaków kontrolnych i markup parsing; 64wiadomości/64KiB historia; nonce hex32, bounded cache64na tożsamość. Per author4/10s oraz global32/10s. Cache i budżety nie powielają obecnego packet bucket.
* Chat wire `{type:"chat_send",text,nonce,generation}`; server `chat_event` z sequence/generation/author_id/author_name/author_role/text/nonce. `chat_history` zawiera generation,first_sequence,messages; walidacja pełna przed atomowym commit. `chat_history_request` z cooldown1s. `chat_rejected` zawiera nonce/reason, więc nie czyści lobby pending ready/name/vote. Klient `send_chat(text:String)->Dictionary`, `chat_snapshot()->Dictionary`, `chat_changed`, `chat_rejected(nonce:String,reason:String)`; pending jest bounded i echo potwierdza. Chat history i event queued za snapshot_end tak samo jak inne catchup messages, tylko dla chat_v1; historia dodawana dokładnie raz i nie może zmienić wcześniejszej kolejności. Rematch czyści historię do nowej generation; reconnect zachowuje aktualny tail. Disabled chat wyświetla wyłączony kompozytor.
* `participant_roster()->Dictionary` zwraca bounded, deep-copied players/spectators ze statusem connected/synchronizing/reserved i nazwą/id; bez IP/tokenów. diagnostic_snapshot dodaje role counts/free spectator slots i bounded transfer details. server_main `diagnostic_roster_json()->String`, `--print-roster` jednorazowy startup JSON, shutdown report zawiera roster. Flagi `--spectators N`, `--lobby-chat` z walidacją przed bind.

## Ryzyka i dowody wymagane

Największy risk: pominięte `for id in slots` lub guard w snapshot/resume. Wyszukać wszystkie użycia slots i sklasyfikować authoring vs recipients, realny test2players+spectator musi strzelić podczas wolnego transferu, reconnect i rematch. Drugi: chat history/live race przy trwającym snapshot — frozen history albo deduplikacja seq po ordered end; test granic frame. Trzeci: spectator disconnect nie może skasować player rematch quorum — oddzielna ścieżka cleanup i snapshot stanu przed/po. Czwarty: rozszerzenie Options.apply musi obsługiwać bool bez traktowania jako liczby; brak walidacji string->float w CLI. Piąty: nowy client na starym serverze może chwilowo uzyskać player reservation zanim wykryje brak role; ograniczenie zgodności jawne, nie deklarujemy odwrotnej kompatybilności obserwacji. Nie implementować zdalnego kick/admin bez potrzeby.
